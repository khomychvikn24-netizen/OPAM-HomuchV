# Лабораторна робота №5. Алгоритми на стеку та черзі

Виконала: Варвара, КН-3/1. Мета: застосувати LIFO та FIFO, перевірити вирази і реалізувати стек поверх масиву.

## Запуск

.NET SDK 10, із кореня репозиторію: `dotnet run -c Release --project lab5/Lab05.csproj`.

## Звіт

Brackets перевіряє (), [], {}, ігноруючи вміст подвійних лапок. Екрановані лапки не перемикають режим. Незакриті лапки самі по собі не вважаються помилкою дужок: решта рядка ігнорується. Індекси від 0; для незакритих дужок повертається індекс першої незакритої відкривальної дужки, для хибної закривальної — її позиція. Параметр own обирає стандартний стек або власний IntStack; в обох зберігаються індекси дужок.

Evaluate розбирає ЗПЗ через Split і TryParse, підтримує +, -, *, /, %. Числа double, роздільник дробової частини — крапка. Другий знятий операнд стоїть ліворуч, перший — праворуч; результат і помилка повертаються через out. Невідомий токен, нестача чи надлишок операндів, ділення або остача на нуль дають повідомлення, а не аварію.

Simulate моделює 11 заявок з Random(29), вагою 1–9 і квантом 2 хвилини. Queue<int> зберігає номери заявок, масиви — залишок роботи, початок першого обслуговування й остаточне завершення. Усі заявки надходять у момент 0; недороблена заявка повертається в кінець. Максимальна черга — 11; загальна тривалість — 70 хвилин.

IntStack має приватний масив, Count, Capacity, Push, Pop та Peek. Початкова місткість 3 % 4 + 2 = 5; шостий Push подвоює її до 10. Виняток порожнього Pop/Peek є вимогою до власного класу: демонстраційні тести його перехоплюють. У робочих алгоритмах кожне зняття захищене перевіркою кількості.

## Обов'язкові тести

| Рядок | Очікувано | Отримано / індекс |
|---|---|---|
| (a[b]{c}) | True | True / -1 |
| ([)] | False | False / 2 |
| )( | False | False / 0 |
| (( | False | False / 0 |
| порожній | True | True / -1 |
| ((()) — 3 відкривальні й 2 закривальні | False | False / 0 |
| "([)]" — лапки є частиною вводу | True | True / -1 |

| ЗПЗ | Очікувано | Отримано |
|---|---|---|
| 3 4 + 2 * | 14 | 14 |
| 5 3 - | 2 | 2 |
| 8 2 / | 4 | 4 |
| 2 3 4 * + | 14 | 14 |
| 5 0 / | Помилка | Повідомлення про нуль |
| 10 4 % 2 * 1 - | K = 3, три операції | 3 |

## Чому саме ці структури

1. **Дужки:** закривається остання відкрита конструкція, отже потрібен LIFO. Черга на рядку ([]) зіставила б ] із (, порушивши вкладеність; список вимагав би вручну підтримувати вершину.
2. **ЗПЗ:** операція використовує два останні ще не використані значення. FIFO на 2 3 4 * + взяв би 2 і 3 для множення та отримав би 10 замість 14; список лише приховав би реалізацію стека.
3. **Заявки:** після кванта наступною має працювати найдавніша заявка, яка чекає, тобто FIFO. Стек відразу повертав би до роботи останню недороблену заявку й змінив би справедливий порядок; List.RemoveAt(0) давав би зайві зсуви.

Queue.Dequeue зсуває індекс початку кільцевого буфера й очищує одну комірку, тоді як List.RemoveAt(0) переносить решту елементів внутрішнього масиву. У лабі №4 100000 Add без місткості зайняли 1,3625 мс, з місткістю — 0,2240 мс, а Insert(0,x) — 443,3604 мс (325,40 раза проти Add без місткості). Це заміри вставки, а не прямий замір Dequeue/RemoveAt: вони ілюструють ціну зсуву того самого внутрішнього масиву; Contains там зайняв 15,3603 мс.

## Висновок

Стек забезпечив правильну вкладеність дужок та порядок операндів ЗПЗ, а черга — циклічне обслуговування заявок. Реалізовано власний стек із подвоєнням і перевірено збіг перевірки дужок зі стандартним. Повний фактичний вивід, включно з Count/Capacity після кожного Push, наведено нижче.
