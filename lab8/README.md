# Лабораторна робота №8. Алгоритми пошуку та їх порівняння

Виконала: Варвара, КН-3/1. Мета: реалізувати узагальнені пошуки, дослідити межі та типові помилки, виміряти окупність сортування.

## Запуск та структура

.NET SDK 10: `dotnet run -c Release --project lab8/Lab08.csproj` із кореня репозиторію.
Search.cs — правильні пошуки; Broken.cs — чотири демонстраційні поломки; Measurements.cs — заміри; Program.cs — Student, генерація, застосування й тести.

Student має поля Name, Group, Score, як у лабі 6. Для великих масивів створено нові записи із Score 0–100 через Random(29); пошук і сортування порівнюють тільки Score. X=53, Y=63, відсутній бал 101. Cmp повертає різницю балів: її знак узгоджений із CompareTo. Для інтерполяції потрібна саме числова відстань, а не тільки знак компаратора; решта пошуків використовує лише знак. Усі пошуки узагальнені за T, жодних спеціальних версій під int чи string немає.

## Завдання 1, 2 та 4: порівняння пошуків

Лічильник збільшується при кожному виклику cmp; для Bound — при кожній перевірці переданої умови. Інтерполяційний варіант має той самий підпис, що й бінарний: перші два порівняння дають числові відстані від нижнього ключа, після чого виконується один пропорційний крок, далі звичайний BinarySearch у відповідному вікні. Відступ обмежується межами масиву, рівні крайні ключі не спричиняють ділення на нуль.

| Запит | Linear індекс / порівняння | Binary індекс / порівняння | Interpolation індекс / порівняння |
|---|---:|---:|---:|
| X=53 | 52365 / 52366 | 53124 / 5 | 52999 / 3 |
| Перший, бал 0 | 0 / 1 | 780 / 7 | 0 / 3 |
| Відсутній, 101 | -1 / 100000 | -1 / 17 | -1 / 3 |

Лінійний пошук відсутнього значення найдорожчий, бо мусить перевірити всі 100000 записів. Різні індекси для наявного ключа допустимі: звичайний бінарний пошук не гарантує першу появу.
Інтерполяційний крок виграє при приблизно рівномірному розподілі числового ключа; на нерівномірному може вибрати невдалу позицію. Наступний бінарний пошук зберігає O(log n), але початкові додаткові порівняння іноді зайві.

## Чотири поломки

1. **lo < hi:** на [53] пошук 53 повертає -1, хоча елемент є; єдиний кандидат не перевіряється.
2. **lo = mid:** на [1,2], ціль 2, після 100 кроків lo=0, hi=1. Оскільки mid=0, межа не рухається; ліміт зупиняє демонстрацію замість нескінченного циклу.
3. **(lo+hi)/2:** на 100000 записів працює — індекс 53124 за 5 порівнянь. Переповнення можливе, коли lo+hi > 2147483647; найменша довжина, що допускає це для коректних індексів, — 1073741825 (lo=hi=1073741824). У unchecked сума стає -2147483648, а mid=-1073741824; такий величезний масив не виділявся, продемонстровано лише арифметику. Безпечна формула lo+(hi-lo)/2 не переповнюється на коректному діапазоні.
4. **Невідсортований масив:** BinarySearch на сирому масиві пропустив 84 із 100 запитів наявних балів, відібраних Random(129). Структура порівняння не дозволяє відкинути половину, коли дані не впорядковані.

## Завдання 3: один пошук межі

Bound приймає монотонну умову виду false…false,true…true та повертає індекс першого true або a.Length. LowerBound отримано умовою Score >= 53, UpperBound — Score > 53.

- Нижня межа — 52365, 17 порівнянь.
- Верхня межа — 53321, 16 порівнянь.
- Останнє входження — **53320**, використано обидві межі, сумарно 33 порівняння.
- Кількість входжень X — **956**, різниця верхньої й нижньої меж; ті самі 33 порівняння.
- Лінійний підрахунок і останній індекс збіглися, але потребували 100000 порівнянь.

Кількість кроків межі визначається поділом діапазону навпіл і не залежить від довжини блоку повторів X.
Умова Score % 7 == 0 немонотонна: Bound повернув 100000 за 16 перевірок, правильна перша позиція — 0. Це фактичний приклад, чому довільний предикат не підходить для бінарного пошуку межі.

## Час та окупність

Release, Stopwatch, прогрів перед кожним видом вимірювання, три заміри й мінімум. Порівнюються пошуки по сирому масиву та сортування його свіжої копії з наступними бінарними пошуками. Клонування виконується поза секундоміром; сортування входить у другий час. Запити однакові для обох способів, із Random(129). На кожному q береться початок однієї й тієї самої послідовності запитів.

У заданому діапазоні q=1…100 сортування не окупилося. Тому додано більші q; перший виміряний виграш отримано на **q=200000**, а попередній q=100000 ще програє. ## Відповіді завдання 6

**Чому поріг більший за лекційні 34?** Наші дані містять лише 101 можливий бал, а в часовому експерименті лінійний пошук працює по невідсортованому масиву: перше входження бала часто трапляється приблизно за сотню перевірок, а не за n/2. Для першої таблиці той самий бал шукається вже в сортованому масиві, де його перша поява може бути далеко від початку. Сортування всіх 100000 записів тому окуповується значно пізніше, ніж модель із різними ключами; також секундомір враховує доступ до пам'яті, виклики делегатів, JIT і Array.Sort, а не тільки кількість порівнянь. Результати не підганялися під 34.

**Два питання, для яких хеш-структури не дають готового пошуку.** Який останній індекс бала 53 у відсортованому масиві? Скільки записів мають бал у [53;63]? Межі впорядкованого масиву дають ці відповіді логарифмічно; сам HashSet не зберігає індексів, кратності та порядку, а звичайний Dictionary не надає пошуку діапазону. Звісно, можна додати окремі лічильники чи індекси, але це вже додаткова структура поверх хеш-таблиці.

**Дані змінюються після кожного запиту.** Для точного пошуку за ключем у потоці виберу Dictionary або HashSet: додавання та пошук очікувано O(1), перевпорядковувати масив після кожної зміни не потрібно. Якщо запитів мало й даних небагато, достатньо перебору. Для частих запитів меж або діапазонів потрібна впорядкована динамічна структура чи окремий індекс: хеш сам цього не замінює.
