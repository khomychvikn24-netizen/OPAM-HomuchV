# Лабораторна робота №4. Алгоритми над списками

Виконала: Варвара, КН-3/1. Мова: C#.

## Мета

Реалізувати побудову списку за критерієм, вилучення під час обходу, лінійне злиття упорядкованих списків і розділення за умовою. Дослідити вартість операцій List<int> через Stopwatch.

## Варіант і запуск

Літера В має номер K = 3. 29 % 3 = 2, 29 % 4 = 1, 29 % 5 = 4.
Основний список: 20 чисел із [-9; 9], new Random(29), Next(-9, 10).
Відбір — додатні непарні; вилучення — значення нижче початкового середнього; розділення — парні та непарні.
Довжини списків для злиття: 10 + K % 5 = 13 та 6 + K % 4 = 9; генератори Random(29) і Random(129).

Потрібен .NET SDK 10. Запуск із кореня репозиторію:

```console
dotnet run -c Release --project lab4/Lab04.csproj
```

Програма виводить результати, запускає автоматичні перевірки та виконує заміри. Для коректного порівняння часу слід використовувати Release.

## Хід роботи та методи

| Завдання | Методи | Принцип |
|---|---|---|
| 1 | PositiveOdd | Новий список зі значень > 0 і з ненульовою остачею від ділення на 2 |
| 2 | RemoveBelowAverageWrongInPlace | Навмисно хибний прямий цикл із RemoveAt(i) |
| 2 | RemoveBelowAverageInPlace | Правильне вилучення з кінця до початку |
| 2 | KeepAtLeastAverage | Новий список зі значень не нижче початкового середнього |
| 3 | GenerateSorted, Merge, IsSorted | Генерація приростами 1–9, злиття двома індексами, перевірка впорядкованості |
| 4 | SplitParity | Розділення на парні й непарні зі збереженням порядку |
| 5 | Benchmark, AddOperation, InsertOperation, ContainsOperation | Прогрів та вимірювання операцій через Stopwatch |

Average обчислює початкове середнє; Copy робить незалежні копії; Equal порівнює результати; PrintSkipped визначає початкові індекси залишених помилковим циклом значень; RunTests перевіряє крайові випадки.
Методи читання не змінюють оригінал. Навмисну зміну позначено InPlace у назві. Відомі розміри задаються місткістю у Generate, GenerateSorted, Copy та Merge; для фільтрації й розділення точні розміри наперед не відомі.
LINQ, сортування та інші заборонені готові алгоритми не використовуються. Contains застосовано тільки в передбаченому умовою замірі.

## Результати

Основний список:

```text
[7, -3, -9, 5, -4, 8, 8, 9, 1, 9, 3, -7, 1, 1, -4, -7, -8, 9, -1, 1]
```

### Завдання 1

Додатні непарні: `[7, 5, 9, 1, 9, 3, 1, 1, 9, 1]`. Count = 10. Оригінал не змінено.

### Завдання 2

Початкове середнє: 19 / 20 = 0,95. Воно обчислюється один раз до вилучень для кожної свіжої копії.

```text
Хибний цикл: [7, -9, 5, 8, 8, 9, 1, 9, 3, 1, 1, -7, 9, 1]
Цикл з кінця: [7, 5, 8, 8, 9, 1, 9, 3, 1, 1, 9, 1]
Новий список: [7, 5, 8, 8, 9, 1, 9, 3, 1, 1, 9, 1]
Збіг правильних версій: True
```

Хибний цикл пропустив **-9 з початкового індексу 2** та **-7 з початкового індексу 15** (індексація від 0). Після RemoveAt елемент праворуч зсувається на поточний індекс, але цикл збільшує i й не перевіряє його. Обхід з кінця не пропускає елементів: зсув стосується вже перевіреної частини.

### Завдання 3

```text
Перший: [8, 11, 12, 19, 22, 31, 40, 49, 55, 64, 70, 71, 77]
Другий: [2, 9, 18, 19, 24, 27, 34, 36, 45]
Злиття: [2, 8, 9, 11, 12, 18, 19, 19, 22, 24, 27, 31, 34, 36, 40, 45, 49, 55, 64, 70, 71, 77]
Упорядкований: True
```

Результат містить 22 елементи, включно з повторами. Після завершення другого списку дописано хвіст першого.

### Завдання 4

```text
Парні: [-4, 8, 8, -4, -8]
Непарні: [7, -3, -9, 5, 9, 1, 9, 3, -7, 1, 1, -7, 9, -1, 1]
Сума Count правильна: True
```

5 + 15 = 20. Від'ємне непарне число може мати остачу -1, тому для непарності використано != 0, а не == 1.

## Замір часу

Фактичний запуск у Release на .NET SDK 10.0.401. Перед кожним заміром виконано прогрів тієї самої операції на 1000 елементів; для Contains — 1000 пошуків у прогрівальному списку з 1000 елементів. Прогрів, виведення та створення списку для пошуку не входять у відповідний замір. Для Add та Insert у час включено створення списку.

| Операція | Час, мс |
|---|---:|
| 100 000 × Add(x), без заданої місткості | 1,3625 |
| 100 000 × Add(x), місткість 100 000 | 0,2240 |
| 100 000 × Insert(0, x) | 443,3604 |
| 1 000 × Contains(-1) у списку 0…99999 | 15,3603 |

Insert тривав менше 30 секунд, тому кількості не зменшувалися. Часи залежать від обладнання, навантаження, JIT і збирання сміття; наведено один фактичний замір, повторний запуск може дати інші числа.

### Відповіді на питання

**1. У скільки разів Insert(0, x) повільніший за Add(x) і чому?**

У цьому запуску Insert був у 443,3604 / 1,3625 ≈ **325,40 раза** повільніший за Add без заданої місткості; порівняно з Add із місткістю — приблизно у 1979,29 раза. List<int> зберігає елементи у внутрішньому масиві. Кожна вставка на початок зсуває всі наявні елементи, тому n вставок потребують близько n(n−1)/2 переміщень і мають час O(n²), тоді як n додавань у кінець — сумарно O(n).

**2. Чому задана місткість дає виграш?**

Без заданої місткості внутрішній масив періодично заповнюється, після чого виділяється більший масив і копіюються наявні елементи. Місткість 100000 одразу резервує достатньо місця й усуває ці розширення. Count при створенні залишається 0: місткість є запасом пам'яті, а не кількістю доданих значень.

**3. Чому Contains тисячу разів довший за сто тисяч Add?**

Значення -1 у списку відсутнє, тому кожен пошук переглядає весь список зі 100000 елементів. Тисяча пошуків охоплює сумарно 100 мільйонів позицій, тоді як додавання виконується лише 100000 разів. Реальна швидкість пошуку залежить також від оптимізацій середовища виконання, але обсяг роботи залишається значно більшим; у замірі пошук тривав 15,3603 мс.

## Крайові випадки

| Вхід | Завдання | Очікувано | Отримано |
|---|---|---|---|
| Порожній список; для злиття обидва порожні | 1–4 | Порожні результати, без помилок | Порожні результати, OK |
| [3] | 1, 2, 4 | Відбір [3]; вилучення лишає [3]; парні [], непарні [3] | Збіг, OK |
| [-3,0,2]: жоден не підходить під відбір | 1 | [] | [], OK |
| [2,2,2]: жоден не нижче середнього | 2 | Обидва правильні способи лишають [2,2,2] | Збіг, OK |
| [1,3,5]: усі підходять під відбір | 1 | [1,3,5] | [1,3,5], OK |
| Усі елементи нижче власного середнього | 2 | Для непорожнього списку неможливо | Математично недосяжний випадок |
| [] і [1,3,5] в обох порядках | 3 | [1,3,5] | Збіг, OK |

Усі елементи непорожнього списку не можуть бути строго нижчими за його середнє: тоді сума була б строго меншою за Count × середнє, що суперечить означенню середнього. Тому цей рядок не позначено як виконаний тест. Для перевірки кількох послідовних вилучень використано [-5,-4,9]: обидва правильні способи повернули [9].

Додатково перевірено незмінність оригіналу, злиття з повторами й дописування хвоста, парність від'ємних значень. Усі 10 автоматичних перевірок пройшли. Для порожнього списку вилучення не обчислює середнє та повертає порожній результат; сам Average для порожнього списку повертає NaN.

## Висновок

Реалізовано чотири алгоритми над списками для варіанта 29. Продемонстровано пропуск елементів при прямому вилученні та перевірено збіг двох правильних способів. Злиття працює за O(n+m), а відбір і розділення — за O(n); повторні RemoveAt можуть вимагати O(n²) часу через зсуви. Заміри підтвердили високу вартість вставок на початок і виграш від попереднього резервування місткості. Для читання вхідних даних оригінальні списки збережено незмінними.
